## Overview

Clustrix is a Python distributed computing framework that runs Python functions on remote compute using a `@cluster` decorator.

Backends, and how far each is actually proven — keep this honest, it is the first thing anyone reads:

| `cluster_type` | Status |
|-|-|
| `slurm` | Verified end to end against a real scheduler |
| `ssh` | Verified end to end against a real GPU host |
| `huggingface` | Verified end to end against real HF Jobs containers |
| `local` | Runs in-process via `local_executor.py` |

That is the whole list — `clustrix.config.SUPPORTED_CLUSTER_TYPES`. Evidence for the verified rows is regenerated by `scripts/verify_cluster_usecases.py` and committed under `docs/evidence/`.

**Backends that are NOT supported.** `pbs`, `sge`, `kubernetes` and the AWS / GCP / Azure / Lambda Cloud VM providers are absent, and naming one in `cluster_type` raises a `ValueError`. So are the cost monitoring and cloud pricing API (`cost_tracking_decorator`, `get_cost_monitor`, `start_cost_monitoring`, `generate_cost_report`, `get_pricing_info`) and the HuggingFace **Spaces** provider — which is a different thing from `cluster_type="huggingface"` (HuggingFace **Jobs**), and that one is supported. Each absent backend is planned for a future update and has a tracking issue; do not document any of them as working:

## Architecture

### Core Components

1. **`@cluster` Decorator** (`clustrix/decorator.py`): Main user interface for marking functions for remote execution. Supports resource specification and automatic loop parallelization.

   **Source availability**: serialization itself does **not** need the function's source — `serialize_function`/`deserialize_function` round-trip a function created by `exec()` and return the correct answer, because dill and cloudpickle work from the code object. The one thing that needs source is loop splitting, which calls `inspect.getsourcelines()`; when the source is unavailable the function runs whole. There is no complexity analysis and no function flattening — those were deleted (#89/#90), so do not document them. Do not describe any of this as "functions cannot be serialized in the REPL" either; that claim is false and led to a fabricated-result bug.

   **Loop splitting is `clustrix/parallelize.py`, and it is the only analyser.** `plan(func)` reads the source, finds a `for` loop (or a single-`for` comprehension statement) at the top level of the function, and classifies every name the body touches as private to an iteration, read-only, or a write-only *collector* (`acc.append(x)`, `acc[k] = v`, `acc += v`, `acc = acc + v`, any discarded-result method call). A loop where every name fits is rewritten into `pre` / `body` / `post` (plus `rest`, the original loop). The body does not write to collectors: it logs each write, and `post` replays the log **in iteration order**, so the result is identical to a sequential run for any type — no associativity assumption, bit-identical float sums. Anything else (a value carried between iterations, `break`, `return` in the loop, a value used after the loop, a change to anything the function did not create, **any** direct use of the global RNG — seeding included, a function defined before the loop that reads a variable assigned later) is refused with the line and reason; `clustrix.explain(func)` prints the decision. A function that only means what it does in one piece is not analysed at all: one with a `global`/`nonlocal` statement, one wrapped by another decorator (`plan` never calls `inspect.unwrap` — the wrapper's code would be skipped), one whose code is not what its source compiles to alone (`_compiles_to`: file edited after import, `super()`, class-private names). Static analysis can prove a loop unsafe but never safe, so run-time checks stand behind it — anything the body reads (values, items, a generator before it is listed) reaching an object a collector can reach; a read-only value or loop item changed by a chunk; the global `random`/NumPy generator state moved; a collected value that cannot be copied, or a closure made in the loop and kept — and a failed check runs `rest` once, in order, on the environment `pre` produced (never `pre` twice). Items are listed before dividing only for containers and iterators that merely walk containers (`__cx_lazy`); a generator, `map`, a file or any other iterator makes the loop run in order, unlisted, because listing it would run the producer before the first iteration. A collector write inside `try`/`with` is postponed only if it cannot raise in practice (`_may_be_deferred`: adding methods, `acc[k] = v`); otherwise the loop is refused. Module-level data the body names is fingerprinted and keeps its identity like everything else. The log never copies an object that existed before the loop: `__cx_dump` writes it as a path (variable or item, then list/tuple index, dict-value position, attribute) and `__cx_load` in `post` puts the original back, so identity survives. A `map_chunks` backend that cannot pickle raises `parallelize.CannotShip`. **What no check sees**: state outside the values the loop was handed (module caches, files, databases, GPU RNG, process-wide settings such as the `decimal` context or cwd), set iteration order and `hash(str)` (per process unless `PYTHONHASHSEED` is set), `sys.argv`, and an object whose pickle omits its state. Every one of these rules exists because an adversarial review produced a silently wrong answer without it; `tests/unit/test_parallelize.py` holds the cases — do not relax one without a replacement check. Say so whenever you describe this feature; do not call it a proof.

   Only a loop at the top level of the decorated function is considered. A loop inside a helper it calls, or nested under `with`/`if`, is not split.

   **Where the chunks run.** Locally: `clustrix/loop_workers.py`, a pool of plain subprocess workers kept between calls — *not* `multiprocessing`, whose `spawn` start method re-imports `__main__` in each worker and so re-runs an unguarded analysis script. `cores` is the number of workers (`-1`: every CPU this process may use; `SLURM_CPUS_PER_TASK` is honoured before the affinity mask). On `ssh`/`slurm`: one job per chunk through `ClusterExecutor`, at most `max_parallel_jobs`, each with the resources the decorator names; the code around the loop runs as its own job unless it only unpacks arguments or returns what was collected (`ParallelPlan.pre_is_cheap`/`post_is_cheap`). There are no SLURM job arrays yet — each chunk is its own `sbatch`. The old protocol (a function accepting hidden `_chunk_range_<var>` keywords and returning a list of chunk results) and `clustrix/loop_analysis.py` are gone; do not document either.

   **`cluster_type` is not a `@cluster` keyword.** `@cluster(cores=8, cluster_type="local")` logs `@cluster received unrecognised option(s)` on every call and is ignored. The backend is set with `configure(cluster_type=...)`. The only extra keywords the decorator accepts are `hf_flavor` and `hf_timeout` (read by the HuggingFace backend) and `data` / `no_data` (paths to add to, or keep out of, the inputs staged for a call). `hf_token`, `hf_username`, `hf_namespace` and `key_file` were once listed as accepted, but no backend ever read them per call; they are configuration and now get the same "no effect" warning. Check every example you write for this mistake.

   **GPUs: `@cluster(gpus=N)`; `auto_gpu_parallel` does nothing.** `gpus` is per job. SLURM: `#SBATCH --gres=gpu:N`, and the scheduler assigns devices. `ssh` and local have no scheduler, so a *divided* loop gets one device group per piece via `CUDA_VISIBLE_DEVICES` (`utils.gpu_device_groups`; `loop_workers.gpu_pool` locally; `job_config["cuda_visible_devices"]` on ssh) and never more pieces than `GPUs // N`; too few GPUs raises rather than running without one. HuggingFace ignores it with a warning (`hf_flavor` is the hardware). `auto_gpu_parallel` is still accepted, warns, and does nothing. **What has been run:** the SLURM request path against a real scheduler whose two `gpu` resources are placeholders (`scripts/setup_local_slurm.sh`, `tests/real_world/test_gpu_requests_real.py`). **No computation has been run on a real GPU, and GPU counting on an ssh host or locally has not been run on a machine that has one.** Do not write otherwise until it has.

2. **ClusterExecutor** (`clustrix/executor_core.py`): Central execution engine. Note that `clustrix/executor.py` is a backward-compatibility shim that re-exports it; the implementation is split across:
   - `executor_core.py` — the `ClusterExecutor` class, dispatch, result retrieval and verification
   - `executor_connections.py` — SSH/SFTP connection management via Paramiko
   - `executor_schedulers.py` — SLURM and SSH submission
   - `executor_scheduler_status.py` — scheduler status polling and error extraction
   - `hf_jobs.py` — the HuggingFace Jobs backend (`HFJobsManager`)

3. **Configuration System** (`clustrix/config.py`): Singleton configuration management supporting:
   - YAML/JSON file loading
   - Hierarchical configuration (defaults → file → runtime)
   - Standard location discovery (the config directory, then the working directory)

**Code, dependencies and data.** What travels with a job, and how it is found:

- *Code.* The function is pickled by value. Project-local modules it uses travel too — by value through cloudpickle, plus a `local_modules` payload registered in `sys.modules` on the worker for imports made inside a function body. (`clustrix/file_packaging.py` and `clustrix/dependency_analysis.py`, an older packager that was never on the execution path and whose output did not run, are deleted; do not document them.)
- *Dependencies.* Read off the pickle and the shipped code (`_payload_import_names`, `required_packages` in `utils.py`). By default the whole local environment is mirrored; `replicate_local_environment=False` installs only what was detected. Remote environments are content-keyed under `<remote_work_dir>/envs/` and reused. **Client and worker must be the same Python minor version**: a cross-version pickle loads and then segfaults when called, so a mismatch is refused at submission.
- *Input files, automatically* — `clustrix/auto_stage.py`, for `ssh` and `slurm`, on by default (`ClusterConfig.auto_stage`). It finds the paths a call names (path-like values among the arguments at any depth; string constants in the function, in the project functions it calls, and in the globals they read), keeps those that exist locally, and makes each resolve on the cluster: used in place if the same absolute path is already there with the same size; otherwise uploaded once over SSH into a content-addressed store under `<remote_work_dir>/data/` and linked into each job directory at the relative path the code uses, or — for an absolute path passed as an argument — the argument is rewritten. **Its limits are deliberate and must be stated with it**: a path found in *code* must be inside the project (git top level, else cwd) after resolving symlinks, while a path passed as an *argument* may be anywhere; credentials are refused; nothing the cluster reports can widen that; above `auto_stage_max_bytes` (1 GB) the call stops and lists sizes. **It cannot see a path computed at run time** (`os.path.join(root, f"{x}.csv")`, a glob, a path read from a config file) — those must be passed as arguments, listed in `@cluster(data=[...])`, or declared. It does not apply to the async path or to HuggingFace Jobs, and **output files a job writes are not brought back** — only the return value is.
- *Declared data* — `clustrix/staging.py` (`data_package`, `DataPackage`, `materialize_packages`, `list_data_packages`, `delete_data_package`, `StagingError`). Two facts that are easy to get wrong: a package too big to inline is uploaded to a **private HuggingFace dataset repo clustrix creates in the user's account**, which an ssh/slurm worker cannot read (that case raises a clear error), and **nothing is ever deleted automatically** — no TTL, no reaper, and `cleanup_on_success` does not touch staged data, including the `auto_stage` store. The user-facing guide is `docs/source/data_packages.rst`.

The `cluster_*` filesystem helpers are read-only: no `cluster_put`, no `cluster_get`.

4. **Utilities** (`clustrix/utils.py`): 
   - Function serialization using cloudpickle/dill
   - Environment capture and replication
   - Cluster-specific job script generation

5. **Filesystem Utilities** (`clustrix/filesystem.py`): Unified filesystem operations for local and remote clusters:
   - **ClusterFilesystem class**: Core implementation handling local and SSH-based remote operations
   - **Convenience functions**: `cluster_ls()`, `cluster_find()`, `cluster_stat()`, `cluster_exists()`, `cluster_isdir()`, `cluster_isfile()`, `cluster_glob()`, `cluster_du()`, `cluster_count_files()`
   - **Data classes**: `FileInfo` for file metadata, `DiskUsage` for directory usage statistics
   - **Automatic connection management**: SSH connections handled transparently
   - **Config-driven**: Uses `ClusterConfig` to determine local vs remote operations

### Key Design Patterns

- **Strategy Pattern**: Different cluster types handled via specific submission methods
- **Decorator Pattern**: Clean API through `@cluster` decorator
- **Singleton Pattern**: Global configuration instance
- **Template Pattern**: Job script generation with cluster-specific variations

### Workflow

1. User decorates function with `@cluster`
2. Function and dependencies serialized with cloudpickle
3. Job submitted to cluster:
   - Remote directory created
   - Serialized data uploaded
   - Python environment setup (venv/conda)
   - Job script generated and submitted
4. Remote execution with unpickling
5. Results polled and downloaded

### Two-venv remote execution

Scheduler and SSH backends do not run the function in one interpreter. `generate_two_venv_execution_commands` (`utils.py`) emits a bash script containing three `python -c "..."` programs:

1. **VENV1 deserialize** — read `function_data.pkl`, write `function_deserialized.pkl`
2. **VENV2 execute** — run the function, write `result_raw.pkl`
3. **VENV1 serialize** — write `result.pkl` and its HMAC tag

VENV1 holds clustrix's own serialization dependencies; VENV2 holds the user's replicated environment. VENV1 never unpickles the user's objects: it moves the envelope's bytes and signs the result. It used to load arguments and results itself, with only dill installed, so any third-party object (a NumPy array) failed there with `ModuleNotFoundError`. Every handoff must use dill/cloudpickle, never stdlib `pickle` — `pickle` serializes a function by qualified name, which cannot be resolved in a fresh interpreter, and that asymmetry is what made remote execution fail for every `__main__` function. **Any change here must keep each serialize/deserialize pair symmetric**; `tests/unit/test_two_venv_execution.py` enforces this.

## Important Considerations

- The project is beta. Version strings live in `pyproject.toml`, `clustrix/__init__.py` and `docs/source/conf.py` and must be kept identical (`setup.py` is a shim that reads `pyproject.toml`).
- SSH-based clusters require proper key setup or password authentication
- **Host keys are verified by default.** Every paramiko connection goes through `clustrix/ssh_security.py::configure_host_key_policy`. Never call `set_missing_host_key_policy(paramiko.AutoAddPolicy())` directly — the opt-out is `ClusterConfig.ssh_host_key_policy="auto_add"`, and it is honoured **only from a trusted configuration source**: `host_key_policy_name` downgrades `auto_add` to `reject` when `config_source_is_trusted` says no, because a weakening of verification is a security decision and it persists in `known_hosts`. `hf_image` follows the same rule, for the same reason — a staged HF job hands `CLUSTRIX_HF_TOKEN` to whatever image it names. On that opt-out clustrix creates `~/.ssh/known_hosts` when it is absent (0700 directory, 0600 file) and loads it with `load_host_keys`, because paramiko's `AutoAddPolicy` persists a key only when `_host_keys_filename` is set — without both steps auto_add accepts every host and saves none. The path has exactly one definition, `ssh_security.user_known_hosts_path`; `ssh_utils` imports it rather than recomputing it.
- Remote environments are recreated from the local environment's freeze output
- Job scripts are bash-based with scheduler-specific directives
- **Every stored credential is released through one function.** `clustrix/credential_release.py::release_credential(target, ...)` is the only place a stored SSH secret is handed out, and its first positional parameter is the recipient — a frozen `CredentialTarget` that names the hostname, the username and *who chose the hostname*. `FlexibleCredentialManager._ensure_credential_unchecked` raises for any caller that is not that module, always, in production. Never obtain a secret any other way: issue #167 was reported as one leak and closed as seven, and seven call sites for one decision is a decision with no home. Provenance is an argument (`ClusterConfig.from_file_content(mapping, source)`), not ambient context. `tests/unit/test_every_credential_goes_through_one_gate.py` fails when a new secret-bearing structure appears anywhere in `clustrix/`.
- **Results are HMAC-verified before they are deserialized.** Loading a pickle executes code, so a file fetched from a remote host is a remote-to-local code-execution path. `result.pkl` is signed with a per-job key and checked by `executor_core.py` before `dill.loads`. Any new remote-origin byte stream the caller parses must be authenticated the same way.
- Automatic cleanup of remote files configurable via `cleanup_on_success`
- **A short job must come back quickly.** `ClusterExecutor` polls for a result starting one second apart and backing off to `job_poll_interval`, which is the ceiling, not the interval. A scheduler manager resolves the remote environment once per set of requirements, not once per submission. Both matter because a divided loop submits many small jobs.
- **The notebook widget** is `clustrix/modern_notebook_widget.py` (behaviour) and `clustrix/widget_style.py` (stylesheet); there is no second widget. Three states are kept apart and must stay apart: the live configuration (`get_config()`, named in the header), each saved profile, and the form — a *draft* that only **Apply** saves and makes live. The header pill says only whether the form is what `@cluster` is using; the outcome of the last action is reported beside the console. "Test connection" and "Run test job" go through `ClusterExecutor`/`HFJobsManager` for real; an unknown host shows its fingerprint and a "Trust this host" button that records exactly the offered key (`ssh_security.trust_offered_host_key`). `ssh_host_key_policy` and `hf_image` are never applied from a profile. Verify any change to it with screenshots in a real Jupyter, light and dark.

## Common Tasks

### Adding New Cluster Type Support

There is **no `ClusterType` enum** — `ClusterConfig.cluster_type` is a plain `str`. The supported values are `local`, `ssh`, `slurm`, `huggingface`, declared once in `clustrix.config.SUPPORTED_CLUSTER_TYPES`.

1. Add the value to `SUPPORTED_CLUSTER_TYPES`; the CLI's `click.Choice` and the notebook widget's backend tiles read that tuple, so they cannot drift apart. Verify rather than trust this sentence — `grep -rn 'SUPPORTED_CLUSTER_TYPES' clustrix/cli.py clustrix/modern_notebook_widget.py` must show both reading it. The widget also needs a display name in `BACKEND_TILES` and a sentence in `BACKEND_DESCRIPTIONS`; without them the tile shows the raw name.
2. Implement submission in the appropriate `executor_*.py` module and dispatch from `ClusterExecutor` in `executor_core.py`
3. Add status checking to `get_job_status` / `executor_scheduler_status.py`
4. Update job script generation in `utils.py` if needed — reuse `job_execution_lines()` rather than writing another variant
5. **Do not mark it supported until a real job has run on real hardware and the evidence is committed.** That gate is why `pbs`, `sge`, `kubernetes` and the cloud VM providers are absent (#140–#146).

### Using Filesystem Utilities
```python
from clustrix import cluster_ls, cluster_find, cluster_stat, cluster_exists, cluster_glob
from clustrix.config import ClusterConfig

# Configure for local or remote operations
config = ClusterConfig(
    cluster_type="slurm",  # or "local" for local operations
    cluster_host="cluster.example.edu",
    username="researcher",
    remote_work_dir="/scratch/project"
)

# List directory contents (works locally and remotely)
files = cluster_ls("data/", config)

# Find files by pattern
csv_files = cluster_find("*.csv", "datasets/", config)

# Check file existence
if cluster_exists("results/output.json", config):
    print("Results already computed!")

# Get file information
file_info = cluster_stat("large_dataset.h5", config)
print(f"Dataset size: {file_info.size / 1e9:.1f} GB")

# Use with @cluster decorator for data-driven workflows
@cluster(cores=8)
def process_datasets(config):
    # Find all data files on the cluster
    data_files = cluster_glob("*.csv", "input/", config)
    
    results = []
    # This loop is divided among workers or jobs: `filename` and `file_info`
    # are private to an iteration, `config` is only read, and `results` is
    # only appended to. clustrix.explain(process_datasets) prints that.
    for filename in data_files:
        # Check file size before processing
        file_info = cluster_stat(filename, config)
        if file_info.size > 100_000_000:  # Large files
            result = process_large_file(filename, config)
        else:
            result = process_small_file(filename, config)
        results.append(result)
    
    return results
```

### Configuration Priority
1. Runtime parameters — `configure(...)` and `@cluster(...)` keywords (highest priority)
2. Configuration file: `config.yml` / `config.yaml` / `config.json` in the config directory (`~/.clustrix/`, or `$CLUSTRIX_CONFIG_DIR`), then `clustrix.yml` in the working directory. `/etc/clustrix/` is **not** searched. `clustrix config ...` and `clustrix load` write the first of these
3. Default values (lowest priority)

There is no environment-variable level. Nothing reads a `CLUSTRIX_<FIELD>`
variable; grep for it before believing otherwise. Only two environment
variables are consulted at all, and neither sets a config field:

- `CLUSTRIX_CONFIG_DIR` — where configuration files are looked for and saved
- whatever `ClusterConfig.password_env_var` names — read by the auth fallback
  to supply a password, and only a password

`save_to_file` omits secret-bearing fields by default, so `password_env_var` is
the only supported channel for getting a credential in without writing it to
disk. A general environment-variable overlay would be a reasonable feature; it
has not been built, and the documentation must not imply it has.

## Testing Guidelines

### The mocking policy, stated once

There is exactly one mocking policy, and it is this one. Do not cite `.claude/CLAUDE.md`'s "do not use mock services for anything ever" against it, or any wording about mocking external dependencies; this list governs.


1. **Real first, always.** A capability may not be marked working until it has been exercised against the real thing — a real cluster, a real API, a real file on disk, a real socket. A test that has only ever passed against a mock is evidence of nothing.
2. **Mocks are a cost-control measure, never a correctness argument.** Once a real call has verified the contract, a mocked test using the *same* call syntax may stand in for it in CI to avoid per-run API fees and credential requirements. Re-verify against the real service when the contract could have changed.
3. **A mock may never be a fallback.** If real functionality is unavailable, the test must fail or raise. Silently substituting a mock turns a broken feature into a green test.
4. **Production code must never know it is being tested.** No `isinstance(x, Mock)`, no test-only branches, no importable module of fake widgets. This is issue #116; `grep -rn "unittest.mock\|MagicMock\|isinstance(.*Mock" clustrix/` must stay empty.
5. **Never weaken a test to make it pass.** If a test fails, fix the code. If the test itself asserts wrong behaviour, say so explicitly and rewrite the assertion — do not quietly relax it.

No test module uses `unittest.mock`: the last three were replaced with tests against real files, real subprocesses and real SSH (issue #117). 1 of the 193 test modules still matches the pattern below, and it is `tests/unit/test_no_mocks_in_shipped_code.py`, which spells the names because it scans shipped code for them. New tests must not add to that number. Recount with `grep -lE "unittest\.mock|Mock\(|MagicMock\(|@patch" $(find tests -name "test_*.py") | wc -l` and `find tests -name "test_*.py" | wc -l` before quoting a figure.

### Test Organization

**Unit Tests** (`tests/` excluding `real_world/` and `integration/`):
- Run in GitHub Actions CI
- No external resources required; fast
- Included in coverage reports

**Real-World Tests** (`tests/real_world/`):
- Test actual cluster functionality, API calls, SSH connections
- `tests/real_world/conftest.py` applies `@pytest.mark.real_world` to **every** item in that directory automatically. Do not rely on a per-file decorator; a file that lacks one is still marked, and a file that has one adds nothing.
- Run manually via the `real-world-tests` workflow (`workflow_dispatch`), which is gated on the required secrets being present

**Integration Tests** (`tests/integration/`):
- **These provision real, billable AWS resources.** They refuse to run unless `CLUSTRIX_ALLOW_BILLABLE=1` is set.
- The guard reads `config.args`, **not** `config.invocation_params.args`. This is deliberate: `invocation_params.args` misses cases that red-teaming the guard turned up. Do not "simplify" it.

### Pre-Push Hook Workflow

A custom pre-push hook (`.git/hooks/pre-push`) automatically runs real-world tests when:
1. Cluster credentials are available (environment variables, etc.)
2. Real-world test runner script exists

**Hook behavior:**
- ✅ **With credentials**: Runs all real-world tests and blocks push on failure
- ⚠️ **Without credentials**: Skips with warning, allows push
- 🔧 **Script missing**: Falls back to basic pytest real-world test run

### External Function Validation

- **External Function Validation**: When testing external functions and features (i.e., anything that we cannot directly test locally), we *MUST* validate that those functions work (without resorting to local fallbacks) at least once before we can check the issue off as completed. Use GitHub issue spec criteria and comments to track what has been validated. We can store API keys, usernames, and/or passwords locally (if we can do so securely) in order to enable this. Once we have verified functionality (again, WITHOUT resorting to fallbacks), we can check off that functionality as "tested" and then use mocked functions or objects in pytests to avoid incurring excessive API fees.
